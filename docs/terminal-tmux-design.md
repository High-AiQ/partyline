# Peek terminal: tmux design spike

## Decision

**No-go for tmux as the default now.** First prototype bounded raw-output replay
with xterm scrollback, retaining the existing pty and transcript architecture. It
is much smaller, cross-platform and avoids another long-lived process and a new
terminal translation layer. It is not a complete terminal snapshot: truncation,
resizes and full-screen applications can make replay wrong. Ship only if the
acceptance experiments below show a material improvement for the affected TUIs;
otherwise investigate a stateful terminal emulator/snapshot protocol before
reconsidering tmux. Do not use terminal output as chat speech.

Today each attachment owns a real pty, initially 120x40 with
`TERM=xterm-256color`; the server feeds pyte, captures plain `screen_text`, then
fans out raw pty bytes. The viewer receives geometry and the plain snapshot,
then bytes; xterm has zero scrollback. Snapshot and subscription are atomic on
the event loop, and a slow viewer is disconnected rather than silently losing
bytes. A late viewer loses colours, cursor position, modes and scrollback. These
are separate problems from any incorrect bytes produced by the application.

## Candidate: one private tmux server per attachment

Launch the agent as a pane in a dedicated tmux server with a unique, restricted
socket and an empty, controlled config; Partyline's pty runs an attached tmux
client. The agent still has a real pty; structured transcript claiming, hooks,
startup delivery and chat remain unchanged. Run server **and** pane inside the
attachment's verified memory scope and write fence, not a shared host server.
Create the socket in a private, accessible directory, never use a default or
user-controlled server, and remove it on all exits. Gate on tmux availability;
Windows retains the current pty path. Pin and test minimum tmux and terminfo
capabilities on Linux and macOS. The tmux client pty output is tmux's rendered
terminal stream, including its UI; do not mistake it for raw pane output.

For a new viewer, `tmux capture-pane -e -p -S - -N` captures retained history
and the current pane with SGR colour escapes and trailing spaces. `-S -` means
start of retained history; `-N` preserves trailing spaces, **not** a history
count. Bound `history-limit`, snapshot bytes and viewer queue. This is text and
styles, not a serialized emulator: it does not restore cursor position, active
screen, input modes, title, hyperlinks or all terminal state. Obtain and encode
necessary state separately, with explicit fallback for unsupported state; alternate
screen capture (`-a`) and history have different semantics. Avoid wrapping or
CR/LF changes when reconstructing the screen. Retained secrets in history and
socket access need the same authorization and lifetime as terminal access.

Live candidates have distinct semantics:

* Attached client output is already available on the outer pty, but contains
  tmux redraws and its terminal protocol, not the pane's original stream.
* `pipe-pane -O` delivers output generated by the pane after the pipe starts;
  it is raw pane output, not tmux's composed display. It is a single pipe per
  pane, so one managed fan-out, backpressure and cleanup are required. A pipe
  command runs in the server's context and must not interpolate untrusted data.
* Control mode (`-C`) provides structured notifications and escaped pane output,
  with flow control and command responses; it needs a correct incremental parser,
  separate client lifecycle and version testing. It is not a byte-identical pty.

Neither an asynchronous capture command followed by a pipe nor subscribing then
capturing is automatically atomic: output can be missed or applied twice.
Design a sequence/barrier protocol, bounded buffering and reconnect on overflow;
prove it under concurrent writes, clears and alternate-screen transitions. Do not
combine a pane capture with tmux client redraw bytes as though they share a
state machine. Multiple viewers must not resize or control the pane independently.
A tmux server with no attached client or a shared server for all attachments
would complicate geometry, isolation, resource accounting and failure cleanup;
a private server is the only tmux option worth prototyping here.

## Candidate: bounded raw replay

Keep a per-attachment ring of approximately 256 KiB of pty output, sized by
bytes, plus fixed geometry and bounded per-viewer queues. Atomically copy the
ring and subscribe on the event loop, send geometry and replay before queued live
bytes, and enable a bounded xterm scrollback. Preserve byte order and incremental
UTF-8 decoding; use binary frames and do not treat the replay as plain text or
apply `convertEol` indiscriminately. Reset xterm on reconnect. Enforce total
memory limits including per-viewer copies and xterm scrollback, and disconnect
slow viewers as today. At 256 KiB per attachment, 100 rings alone use about
25 MiB, before copies and browser memory. Keep existing authorization checks.

A ring may start inside UTF-8 or an escape sequence, after a required mode or
colour setting, or in the middle of an alternate-screen session. Redraws,
resize/reflow and terminal queries may not replay correctly, and old output can
contain sensitive content. A fixed byte limit is not a reliable screen boundary;
do not claim exact recovery or use a plain pyte snapshot to fill the gap, since
it can duplicate or corrupt subsequent state. Test truncation explicitly, measure
real traces and explore reset/checkpoint boundaries or a proper stateful snapshot
if replay fails. No persistence across restart is proposed.

## Comparison: Orca and a Partyline-owned service

[Orca's terminal documentation](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/terminal.mdx)
describes an xterm.js UI and a terminal daemon. Its
[package manifest](https://github.com/stablyai/orca/blob/main/package.json) lists
`node-pty` and an xterm WebGL addon; dependency presence alone does not prove
which renderer or fork is active in every configuration. Its
[SSH documentation](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/ssh.mdx)
says a relay keeps remote PTYs alive across app closure and restores scrollback;
remote terminals require node-pty. Its
[remote server documentation](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/remote-servers.mdx)
says the terminal host survives server restart and describes optional per-terminal
systemd memory scopes. The
[headless emulator source](https://github.com/stablyai/orca/blob/main/src/main/daemon/headless-emulator.ts)
uses xterm state and tracks incomplete escape sequences. These sources establish
separate ownership and stateful emulation; they do not establish that every local
configuration uses the same transport, a Unix socket JSON-RPC protocol, or tmux.
A reported [reattach failure](https://github.com/stablyai/orca/issues/19857)
and [garbled resize case](https://github.com/stablyai/orca/issues/21204) are
user reports, not proof of universal behaviour or of fixes in a particular release.

A Partyline-owned persistent pty/screen service is a third Partyline design:
move pty ownership, bounded stateful emulation and fan-out into a separately
supervised service, with an authenticated local protocol and explicit session
identities. It can keep real processes and screen history across server restarts
without tmux's extra terminal layer; unlike raw replay, it can maintain state
from process start. **Inference:** this could improve fidelity and continuity,
but a serialized screen still needs a proven cursor/mode/partial-sequence and
snapshot-to-stream boundary, as well as bounded history and backpressure.
Unlike per-attachment tmux, Partyline owns the emulator, protocol and recovery
semantics. A shared service adds a shared failure domain and needs per-attachment
fence and cgroup enforcement, access isolation, process exit ownership, upgrades,
version negotiation, orphan policy and transcript/hook reattachment. A separate
service is therefore not a free substitute for the replay prototype; restarting
or adopting a process is a product and safety decision independent of rendering.

The recommendation remains replay first. If its fidelity fails, compare a
stateful emulator in the existing server against a persistent service and tmux:
prototype the smallest option that passes the same input, rendering, lifecycle,
resource and security gates. Estimate a persistent-service prototype at 2–4
engineering weeks before hardening, depending on cross-platform process and
recovery requirements; it is not an approved implementation.

## Experiments and outstanding gates

Scratch experiment, 2026-10-28: Linux, tmux 3.6, empty config, isolated socket,
shell pane, in an existing verified cgroup (`memory.max` 6 GiB). This was not a
full Partyline launch or a TUI compatibility test. The tmux server and pane
remained in that same cgroup despite daemonisation; their RSS was approximately
4.6 MiB and 4.1 MiB respectively, including the shell. This is one observation,
not a per-attachment budget or proof for systemd scope plus bubblewrap/macOS.
The server and pane had distinct session/process-group IDs. Terminating the
attached client's process group left both alive and the session accessible;
`stop_process_group` alone is insufficient. An explicit `kill-server` cleaned up
the scratch session. After 30 numbered lines, capture included early history and
reported history size 9; a colour capture contained SGR red and a pipe saw the
original red and alternate-screen escape sequences. Resizing a detached window
changed its reported geometry from 40x10 to 70x15. Capturing the saved alternate
screen after exiting it returned an error in this run. These checks establish
neither visual fidelity nor an atomic capture/live boundary.

Before any tmux implementation is accepted, run and record:

* **Scope and fence:** verify server, pane, pipe helper and descendants by PID,
  cgroup `memory.max`/`memory.current`, and sandbox write-denial probes in the
  actual scoped, fenced launch; verify no client can attach to another socket.
  Include failure and OOM cases, macOS address-space accounting, and memory at
  idle and with bounded history under multiple concurrent attachments. Fail
  closed if the cap or fence cannot be proved. A daemon in the same cgroup in
  this scratch test does not prove all launch paths; unlike a host container
  daemon, a fork normally inherits its cgroup unless explicitly moved.
* **Stop and restart:** test stop, forced client death, server crash and orderly
  and unplanned Partyline restart, checking every PID and socket. Explicitly
  kill the private server and verify the scope empties, escalating through the
  existing scope cleanup. Default policy is no surviving sessions: automatic
  recovery currently marks old attachments exited and starts fresh/resumes from
  transcripts. Reattachment could preserve work, but requires durable identity,
  transcript claims, fresh hook credentials, admission and orphan cleanup; do
  not silently adopt survivors or allow duplicate agents. Verify exit status and
  status transitions refer to the pane, not merely the tmux client.
* **Input and size:** exercise ordinary keys, Ctrl-C, escape, Unicode, large and
  bracketed pastes, and startup prompt delivery exactly once, both direct and
  browser paths. Test tmux prefix interception and terminal query responses,
  including avoiding duplicate replies. Verify hook environment, token rotation,
  cwd and argv survive the launch wrapper. Fix pane geometry at the existing
  authoritative size; test resize, SIGWINCH, reconnect and competing viewers.
* **TUIs:** run Claude, Codex and opencode interactively under their normal
  fenced and capped launch, with permission appropriate to a scratch session.
  Compare baseline, replay and tmux: initial prompt, colour, cursor, Unicode,
  scrolling, mouse, bracketed paste, alternate-screen entry/exit, resize, redraw,
  long output, simultaneous viewers and reconnect during output. Check live and
  late views, including truncated replay; preserve transcripts as the only speech
  source. Windows must retain and test the current path; evaluate replay there.

These TUI, full fence, scoped shutdown, hook and restart tests have **not** been
run in this spike. The shell experiment does not establish their behaviour.

## Stages and go/no-go

1. **Replay prototype, 2–4 engineering days:** ring, atomic handoff, binary
   handshake, bounded xterm scrollback and focused tests. Capture representative
   TUI traces and compare early/late viewers, reconnect, overflow and Windows.
2. **Evaluate, 1–2 days:** reproduce reported failures and compare screenshots
   and interaction against a directly attached terminal. Go only if replay
   materially improves all three TUIs without corrupted visible cells, lost or
   duplicated live output, broken input, or unbounded memory in the agreed test
   matrix. Otherwise do not ship it; investigate stateful snapshots.
3. **Optional tmux research, 4–8 days:** only if replay fails and a stateful
   snapshot cannot solve the issue economically. Prove the scope, fence,
   lifecycle, exact snapshot/live handoff and TUI gates above; measure memory.
   No-go if cleanup, accounting or handoff cannot be proved, or if tmux adds
   regressions. This is a prototype estimate, not permission to ship.
4. **Production hardening, 3–6 days after a successful prototype:** platform
   fallback, security/lifecycle integration, failure tests, documentation and
   normal release gates. Re-estimate after experiments; prefer the smallest
   solution meeting the same acceptance criteria.
